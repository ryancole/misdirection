# misdirection

Firmware for a [Teensy 4.1](https://www.pjrc.com/store/teensy41.html) that
presents to a target PC as an ordinary USB keyboard and mouse, and takes its
orders from a separate controlling PC over a serial link. The target sees a
standard HID device; the control channel is out of band, on a UART the target
never touches.

```
controlling PC ──USB-serial──> [PL2303] ──UART (Serial1)──> [Teensy 4.1] ──USB HID──> target PC
                                                framed protocol            keyboard + mouse
```

The main firmware is `src/misdirection/`. The other sketches are the bring-up
steps that lead to it, kept in the tree because each is a fast way to localize a
fault later.

## How it works

The controlling PC sends 8-byte framed messages over `Serial1` (pins 0/1). The
firmware owns the HID report state and translates each message into a USB
keyboard or mouse report on the target. Raw HID usage codes go on the wire — no
ASCII, no virtual-key codes — so keyboard layout and dead-key handling stay the
host's problem and never enter the firmware.

The wire format and every message's semantics are specified in
[PROTOCOL.md](PROTOCOL.md), which is the contract `src/misdirection/misdirection.ino`
implements. Change one, change both. Machine-readable test vectors for both
directions live in [etc/protocol-vectors.json](etc/protocol-vectors.json)
(generated by [etc/gen-vectors.py](etc/gen-vectors.py)).

Two safety mechanisms are built in:

- **Arm gate.** Nothing that produces input takes effect until **pin 2 is
  grounded**. While disarmed, input messages are dropped and the firmware
  answers `NACK(4)` (throttled). `PANIC`, `PING`, and `SCREEN_SIZE` are always
  honored. The onboard LED is lit while armed.
- **Panic.** `PANIC` (message `0x00`) releases every held key and button and
  resets internal state, regardless of arm state, so a stuck modifier can always
  be cleared without touching the board.

## Layout

```
src/
  misdirection/        the real firmware: framed protocol on Serial1 -> USB HID
  hid_smoke_test/      step 2: ground pin 2, board types and moves the mouse
  uart_echo/           step 3: UART loopback only, no HID (USB Type = Serial)
  uart_to_hid_naive/   step 4: throwaway byte-in -> keystroke-out bridge
etc/
  build.ps1            compile a sketch for the Teensy 4.1
  upload.ps1           compile and flash the connected Teensy
  common.ps1           shared helpers, incl. the per-sketch USB Type table
  gen-vectors.py       regenerates the protocol test vectors
  protocol-vectors.json
  test.ps1             build and run the host-side firmware tests
test/
  protocol_test.cpp    parser/dispatch tests that #include the real sketch
  stubs/Arduino.h      just enough fake Teensy core to compile it natively
PROTOCOL.md            the host <-> Teensy wire protocol
```

Each sketch needs a specific Teensy **USB Type** (e.g. `usb=hid` vs
`usb=serial`); a wrong one fails in confusing ways (a `serial` build links no
Keyboard/Mouse; an `hid` build gives the target no CDC port). Rather than living
in IDE menu state, that setting is recorded per sketch in the `$SketchUsbType`
table in [etc/common.ps1](etc/common.ps1) and the build scripts apply it
automatically.

## Building and flashing

Requires **Arduino IDE 2.x** with the Teensy (Teensyduino) board support
installed — the scripts use the `arduino-cli` bundled inside it, so there is no
separate toolchain to install. Windows / PowerShell 7.

```bash
# List the sketches and the USB Type each will build with
etc\build.ps1

# Compile one sketch
etc\build.ps1 misdirection

# Compile every sketch (a cheap sanity check before committing)
etc\build.ps1 -All

# Compile and flash the connected Teensy
etc\upload.ps1 misdirection

# Show the Teensy port and the PL2303 COM port
etc\upload.ps1 -ListPorts
```

Both scripts take `-UsbType` to override the recorded default, `-Clean` to wipe
the build cache first, and `-DryRun` to print the `arduino-cli` command without
running it.

## Testing

The parser and dispatch logic is tested natively, without a board:

```bash
etc\test.ps1
```

[test/protocol_test.cpp](test/protocol_test.cpp) `#include`s the real
`misdirection.ino` over a stub Teensy core in [test/stubs](test/stubs), feeds it
byte streams, and checks what came back on `Serial1` and what reached the fake
`Keyboard`/`Mouse`. It needs Visual Studio with the C++ workload (found via
`vswhere`). In VS Code it is the default test task (**Firmware: Test**).

### From VS Code

[.vscode/tasks.json](.vscode/tasks.json) wires the same scripts to tasks that
act on the open sketch:

- **Arduino: Build** (default build task) — compile the open sketch
- **Arduino: Build all** — compile every sketch in `src/`
- **Arduino: Upload** — compile and flash the open sketch
- **Arduino: List boards** — show the Teensy and PL2303 ports
- **Firmware: Test** (default test task) — build and run `test/` natively

## Wiring

Adafruit 954 PL2303 USB-serial cable (3.3 V logic) between the controlling PC
and the Teensy:

| Cable | Signal | Teensy      |
|-------|--------|-------------|
| black | GND    | GND         |
| green | TXD    | pin 0 (RX1) |
| white | RXD    | pin 1 (TX1) |
| red   | 5 V    | leave disconnected |

The white wire makes `Serial1` bidirectional, which is what gives the firmware a
back-channel for `PONG`/`NACK`. Serial settings are **115200 8N1**, no flow
control.

The Teensy's own micro-USB goes to the **target** PC — flashing the board
changes what the target sees.
